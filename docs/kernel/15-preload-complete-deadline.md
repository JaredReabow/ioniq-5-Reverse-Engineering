# The timeout is an internal `preload-complete` deadline, not a config knob — and the three ways forward

Date: 2026-11-06. Doc 14 showed 4/6/8 vCPUs all lose the registration race. A strings pass over the
launcher settles where the deadline lives, and it is not configurable.

## What the launcher strings say

```
registerFromApploadTimeout(int, const QString)
registerFromApploadTimeoutSlot(int, const QString)
[TIMEOUT] Preload complete signal is generated by timeout
```

- There is **no `timeout=` / `timeoutMs` key** and no config file carrying one: the launcher's only JSON
  (`/rw_data/applaunch-config.json`) does not exist on a running unit (`J1_EXISTS=no`), and `autotest.conf`
  is the manufacturing app's. The deadline is **internal to `AppLauncher`** — a patch or nothing.
- The timeout is **not** "the app is slow to start". It is "the app is slow to emit its
  **preload-complete** signal": launcher launches the group → waits for each app's preload-complete → the
  timeout fires and the launcher *synthesises* the signal → the app's real registration lands ~3 ms later
  → `Already registered` → deregister. This is why more vCPUs moved the name-owned time (+100 s → +85 s)
  but never moved the 3 ms margin.

## The negative already on the record (do not re-measure)

4, 6 and 8 vCPUs all lose the same race, with the same 129,844-byte standby capture and the same pid
change across two samples (doc 14). That is a measurement, and it is the thing that saves the next person
three runs.

## The three options, in order

1. **Leave it.** The projection already has the app painting its own standby face at 1920×720 on the
   stock display backend, a socket, and a connected client; the laid-out frame already exists from the
   headless path (doc `docs/vm/38`). The remaining gap is a vendor timing constant under TCG, and
   *"the vendor launcher deregisters the app under TCG"* is a legitimate, log-provable limitation.
2. **Patch the deadline** in `AppLauncher` — a labelled substitution like the compositor wrapper and the
   input module. Requires locating the constant (value + units) in the binary first; not yet done.
3. **Emit the preload-complete signal ourselves** — a stub that sends what the app would send, so the
   launcher's deadline never fires. Cheapest of the three *if* the signal is identifiable on the bus, and
   it does not touch a vendor binary — but it is a substitution too, and must be named as one.

## Recommendation (this doc's position, not a conclusion)

Option 3 is the one to spend the next run on, because it is the only one that needs no vendor-binary edit
and no reverse-engineering of a constant — it needs the **signal identity**. The log already names the
apps that time out and their group; the bus traffic at that moment will name the signal
(`dbus-monitor` on the session bus, filtered to the launcher's `com.lge.…appmanager` interface). Once the
signal name and signature are known, the stub is small and the whole thing is one injection.
