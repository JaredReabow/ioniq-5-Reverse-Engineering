# The deadline patch does not stop the timeout — `[TIMEOUT] [2 Group] AppID : 11` still fires

Date: 2026-11-06. The `QTimer::setInterval` immediate at `0x18270` was patched `0x2710`→`0x7530`
(10 s → 30 s), as the fifth substitution, and the doc-21 sequence was re-run. The patch is verified in
the binary; the timeout still fires.

## The patch (fifth substitution), applied and verified

- `/app/bin/AppLauncher`, file offset `0x18270`: `be 10 27 00 00` → `be 30 75 00 00`
  (`movl $0x2710,%esi` → `movl $0x7530,%esi`).
- Combined with the surface-id patch (doc 20) at `0x475e8`. sha256 `24f054dc…` → `f208958c…`.
- Verified in the injected image: `xxd -s 0x18270` = `be 30 75 00 00`.

## The decisive textual check — the timeout did not disappear

From the launcher log (`/tmp/applauncher-stdio.log`, decoded this run):

```
"m_AppProcess->start(/app/bin/AppHomeScreen) PID[2272] | 21:39:22.948"
"[TIMEOUT] Preload complete signal is generated by timeout   | 21:40:11.359"
"[TIMEOUT] [2 Group] AppID : 11, PID : 2272                    | 21:40:11.488"
"[REGISTERED] registeredFromNativeApp AppId[11][AppHomeScreen] | 21:40:11.526"
"[REGISTERED ERROR] Already registered AppId[11][AppHomeScreen]| 21:40:11.603"
"[onDemandAppKill] … appId[11][AppHomeScreen] is killed by AppManager | 21:40:11.624"
```

`[TIMEOUT] [2 Group] AppID : 11` **still fires** — ~48.5 s after the process start, not 10 s and not
30 s — and the app is still killed. The app's registration takes ~48.5 s under TCG, so it still lands on
the wrong side of the deadline.

## The honest reading

The fifth substitution did **not** stop the deregister. Two possibilities, both recorded, not chosen:

1. The timer patched at `0x18270` is **not** the app-load deadline that emits `[TIMEOUT] [2 Group]
   AppID : 11` (the fired time, ~48.5 s, matches neither the old 10 s nor the new 30 s immediate).
2. The deadline is correct but the app's ~48.5 s registration is still beyond it, so a larger value
   (the 60 s immediate `0xea60`) or a different timer is needed.

This is a **negative result about the patch**, and it sharpens the question: the timeout fires at ~48.5 s,
which is a measurement the next patch must explain before it is made.
