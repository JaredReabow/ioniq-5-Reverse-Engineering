Configured credential observations
----------------------------------
ApplicationLauncher.service has no User=, Group=, SmackProcessLabel=,
CapabilityBoundingSet=, AmbientCapabilities=, NoNewPrivileges=, or namespace
isolation directive. AppLauncher.sh starts /app/bin/AppLauncher 3 without a
credential or label change. Exact AppLauncher imports QProcess::start but no
direct setuid/setgid/setresuid/setresgid/capset/setgroups/initgroups call.

For an ordinary root execution without file capabilities, upstream Linux v4.1
cap_bprm_set_creds derives the new permitted set from the old bounding set when
the effective uid is zero and makes the effective set equal to permitted. The
recovered exact function occupies [0xffffffff811b85a2,0xffffffff811b89d6).
This predicts, but does not runtime-prove, broad permitted/effective capability
inheritance for the configured UID-zero launcher and app children.

SMACK observations
------------------
/etc/smack_setup.sh writes Privileged to /sys/fs/smackfs/onlycap. Therefore a
floor task is not eligible for smack_privileged() solely because it has uid 0
or ordinary capability bits.

Recovered policy includes reciprocal explicit rules between floor '_' and
enumerated App::* domains, including App::manager, App::navi, App::mediaplayer,
and App::upgrade. The upgrade policy separately grants App::upgrade broad
access to '*', '_', and Privileged. This does not make floor equivalent to
App::upgrade or Privileged.

/etc/update_start_5w.sh.ori recursively deletes labels and restores
SMACK64EXEC only for enumerated executables. It restores AppUpgrade with
SMACK64EXEC=App::upgrade but omits systemd, init, AppLauncher.sh, and
AppLauncher. In the recovered kernel, exec with no inode execute label retains
the inherited task label.

Exact systemd ambiguity
-----------------------
The exact /lib/systemd/systemd embeds 'systemd 225' banner strings while its
embedded build paths and RPM inventory identify systemd 249.3-r0mango134. Exact
dynamic relocations include prctl, fsetxattr, lsetxattr, and cap_set_proc, but no
fgetxattr/getxattr relocation was found. This record does not infer executable
SMACK label behavior from either upstream version alone.

Storage and boot observations
-----------------------------
The recovered kernel command line identifies root=/dev/mmcblk0p3 rootfstype=ext4
and init=/lib/systemd/esinit, without an explicit ro/rw token. Linux defaults
such a root mount to read-only until userspace remounts it. checkroot.sh contains
a default root mode/options of rw, but its successful use and the owner unit's
live root flags are unobserved. fstab_emmc contains /log_data, /update,
/voicememo, /rw_data, and three /Data/* entries without a read-only option;
runtime mounts, labels, and actual write access are not established by static
configuration.

The recovered kernel has no dm-verity, IMA appraisal, EVM, or module-signature
enforcement configured. This removes named runtime integrity mechanisms only;
it does not establish write access, executable-object stability, update
acceptance, inactive-slot selection, ABL/MICOM boot acceptance, anti-rollback,
health, mark-good, or persistence. OEM update/boot trust remains a separate
boundary rooted in the ABL.oemkm/oemkm handoff and signature/manifest paths.

Passive collector extension
---------------------------
tools/uk_fw/bench_state_bundle.py now emits read-only records for every observed
process's PPid, CapInh, CapPrm, CapEff, CapBnd, optional CapAmb, optional
NoNewPrivs, and Seccomp fields. Stock Linux v4.1 omits the NoNewPrivs status
line, so absence is recorded as unavailable. The host parser deterministically decodes Linux v4.1 capability
bits through CAP_AUDIT_READ while preserving unknown bits. It also records the
read-only sysctls kexec_load_disabled, modules_disabled, dmesg_restrict, and
mmap_min_addr; hashes systemd/esinit/AppLauncher.sh/update_start_5w.sh.ori; and
queries SMACK64/SMACK64EXEC for the launcher chain, relabel script, systemd, and
/tmp. The probe does not write, remount, signal, start a service, or execute a
recovered target.

Verdict
-------
The strongest configured post-entry hypothesis is:

  stock App::* code (configured uid 0, capabilities unobserved)
    -> conditional AppLauncher V-028 direct execution
    -> floor '_' task label if the selected executable lacks SMACK64EXEC
    -> explicit floor-to-enumerated-App access

This is a same-uid SMACK-domain amplification candidate, not a completed root or
persistence chain. The missing gates are runtime D-Bus registration/delivery,
caller-controlled executable object stability, successful exec, actual uid/gid/
groups/capability/securebits/namespaces/SMACK state, useful floor-authorized
objects, update-anchor reachability, authenticated-byte continuity, partition
write, next-boot activation, boot acceptance, health, mark-good, rollback, and
recovery.
