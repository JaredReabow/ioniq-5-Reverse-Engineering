Primary surface classification
------------------------------
AppNavi's NimoExSLScreenLinux constructor at 0x335b080 constructs QQuickView.
The recovered QQuickView(QWindow*) constructor is at 0x2735d0 and reaches
QQuickWindowPrivate::init at 0x1b0160. That initializer calls
QWindow::setSurfaceType at 0x1b02f6 with the result of render-loop virtual
windowSurfaceType(). The recovered QSGRenderLoop implementation at 0x178680
returns 1, which Qt's QSurface enum defines as OpenGLSurface.

This resolves the earlier class ambiguity: the primary Qt Quick window is an
OpenGL surface and uses the recovered Wayland EGL client integration, not the
Shm window route. Independent AppLauncher/Weston runtime records bind that
primary AppNavi window to IVI surface ID 3000. AppNavi's separate
createExSLEglSurface(type=2) call is an ExSL enum and is not used as the Qt
surface-type proof.

Common QtWayland false-visibility branch
-----------------------------------------
Public QtWayland v5.4.1 defines QWaylandWindow::WindowType as Shm=0 and Egl=1.
Its public QWaylandWindow::setVisible(false) source unconditionally attaches a
null buffer and commits after the delete guard survives.

The recovered QWaylandWindow::setVisible(bool) is [0x63ce0,0x63ec1). On false
visibility it calls virtual windowType() through slot +0x60 at 0x63dbd. Only a
zero return reaches attach(nullptr,0,0) at 0x63ea9 and commit at 0x63eb2. The
recovered QWaylandShmWindow::windowType() at 0x67870 returns zero. The recovered
EGL implementation at 0x80e0 returns one. Thus the common false-visibility path
explicitly detaches Shm but skips that detach for Egl.

AppNavi hide producers and Qt Quick dispatch
---------------------------------------------
The complete recovered AppNavi direct-call inventory contains two calls to its
QWindow::hide() import and no direct tail transfer to that import:

- 0x3362275 in NimoExSLScreenLinux::onForeground(bool,bool), body
  [0x3361df0,0x3362c7d);
- 0x3365140 in NimoExSLScreenLinux::dispatchNotifyEvent(ExSLNotifyEvent const*),
  body [0x3364fe0,0x3365c97).

The first path calls NimoExSLScreen::onForeground at 0x3361e27. That base calls
ExSLScreen::onForeground at 0x33712c3. The direct Linux hide branch is entered
only when the returned Boolean is true. It then admits screen IDs 1, 2, or 4 and
requires the logical foreground argument to be false before calling hide at
0x3362275. Other screen IDs do not reach that direct hide call through this
branch.

There is also a queued visibility route. ExSLScreen::onForeground(bool,bool),
body [0x2607730,0x2607c85), has a Gen5/platform-specific same-state branch: when
the requested foreground Boolean equals its byte at +0x18 but differs from its
byte at +0x4c, platform code is 6, and platform generation is 5, it constructs
an ExSLNotifyEvent whose type field +0x30 is 0x103 and whose value field +0x34 is
the requested Boolean. The event is queued back to the same screen at
0x2607af7.

NimoExSLScreenLinux::dispatchNotifyEvent loads the type at event +0x30 and
selects 0x103 at 0x33650f3..0x33650f8. Its retained diagnostic format is
`setVisible screenId(%d) value(%d)`. A zero event value reaches QWindow::hide()
at 0x3365140; a nonzero value reaches QWindow::show() at 0x3365338. The local
same-state producer returns false after queueing, so the Linux override skips its
direct-hide branch and the queued event remains a distinct visibility route.
This proves a genuine onForeground -> queued visibility event ->
dispatchNotifyEvent -> Qt hide/show architecture. It does not prove that every
type-0x103 event is locally created by that branch or that this branch executed
in a retained run.

The complete in-binary direct-call inventory for
SessionInteraction::setForegroundStatus(unsigned short,bool,bool) at 0x1c3a930
contains six calls:

- 0x1c3bca7 in SessionInteraction::updateServiceState(unsigned short,
  ExSLEventBase*,bool);
- 0x2d98d7b and 0x2d9903e in
  CSystemControl::onSplitScreenStateChanged(bool);
- 0x2daa4a0, 0x2daa51b, and 0x2daa573 in
  CSystemControl::changeWindowStatus(ecScreenId,ecWindowStatus).

At 0x1c3bca7, a parsed-event result bit 0x100 and true
isUnificationPlatform() predicate select the call; status is true exactly when
event field +0x30 equals 0x0a, and beforeNotify is false. The other five direct
calls pass beforeNotify=true. Thus retained `beforeNotify(0)` diagnostics are
consistent with 0x1c3bca7 among the recovered direct callers, but static caller
inventory does not prove the runtime callsite or exclude indirect invocation.

Selected basic render-loop hide
-------------------------------
The retained integrated Home-to-Navigation runs under diagnosis explicitly
export QSG_RENDER_LOOP=basic. Recovered basic-loop vtable address point 0x60fce0
has its +0x68 relocation at 0x60fd48, resolving to 0x178730. Public v5.4.1 binds
that method to QSGGuiThreadRenderLoop::hide(QQuickWindow*).

The exact recovered routine at 0x178730 obtains QQuickWindowPrivate and tail
jumps to sceneGraphAboutToStop at 0x1aacd0. It does not remove the window,
release the scene graph, call QOpenGLContext::doneCurrent(), invalidate the EGL
surface, or attach a null Wayland buffer. Public v5.4.1 agrees: ordinary basic
hide only calls fireAboutToStop(); basic-loop GL cleanup/doneCurrent belongs to
windowDestroyed(), not ordinary hide.

Threaded obscure route
-----------------------
Recovered threaded-loop vtable address point 0x61df58 has its +0x68 relocation
at 0x61dfc0, resolving to 0x1802a0. Public v5.4.1 identifies this as
QSGThreadedRenderLoop::hide(QQuickWindow*). If the window is exposed, it calls
handleObscurity(), which posts WM_Obscure and waits for the render thread. The
WM_Obscure handler calls fireAboutToStop(), QOpenGLContext::doneCurrent(), and
then clears the active-window pointer. The recovered event-handler sequence
contains the corresponding doneCurrent import call at 0x1831f6 followed by the
active-window clear at 0x1831fb. This path is conditional on the threaded
window/render-thread state; source reachability is not runtime execution proof.

Recovered EGL invalidation edge
--------------------------------
QOpenGLContext::doneCurrent() is at 0x121380 in the recovered QtGui library. At
0x1213d4 it calls platform-context virtual slot +0x30. The recovered Wayland EGL
platform-context vtable address point is 0x20d2a0; relocation 0x20d2d0 resolves
its +0x30 slot to 0x6aa0.

The 0x6aa0 implementation calls eglMakeCurrent with no current surfaces/context,
then invokes virtual slot +0xf8 on its associated Wayland window at 0x6ad3 and
clears the current-window pointer. The QWaylandEglWindow vtable address point is
0x20d538; relocation 0x20d630 resolves its +0xf8 slot to 0x82c0.

The recovered 0x82c0 routine conditionally destroys the EGL surface, clears its
stored handle, calls QWaylandWindow::attach(nullptr,0,0) at 0x8310, commits the
wl_surface at 0x8319, and flushes the display. This recovered vendor behavior is
stronger than the public v5.4.1 invalidateSurface() body, which only destroys the
EGL surface. The separate destructor region beginning at 0x8120 also destroys
the native wl_egl_window and must not be conflated with ordinary invalidation.

Result
------
The retained harness changed this contract by forcing the basic loop. For an
AppNavi OpenGL/EGL QQuickView, common QWaylandWindow false visibility skips the
Shm-only detach, and selected basic-loop hide stops at fireAboutToStop(). It
therefore omits the threaded doneCurrent -> QWaylandEglWindow invalidation ->
null-attachment/commit route capable of creating the compositor zero-size/BG
condition needed by ApplicationManager's Navigation-window latch.

This is an exact harness-specific semantic mismatch and a direct explanation
for why a genuine false-visibility callback can coexist with no AppNavi BG in
the retained basic-loop runs. Producer analysis now also shows that waiting only
for a primary NimoExSLScreenLinux::onForeground(false,...) diagnostic is too
narrow: AppNavi has a second direct hide at the type-0x103 visibility-event
consumer, and the first retained false-visibility callback precedes all retained
setForegroundStatus/onForeground screen diagnostics in that launch interval.
It does not prove which hide producer executed, that this is the only runtime
problem, or that a future threaded run will complete Navigation. The mixed
vendor-EGL/project-Mesa VM stack, exposure state, actual WM_Obscure execution,
child stderr routing, compositor delivery, setter replay, callbacks, and final
current/drawing ID 30 remain runtime boundaries.

AppLauncher child-channel routing
---------------------------------
AppLauncher's process-start body is [0x163f0,0x18550). It reads app ID from
AppProcess+0x20 at 0x16f78. For IDs at most 40, the mask at 0x17a48 exempts only
17, 22, and 40; ID 30 is not exempt. The remaining exemption at 0x16f84 requires
AppProcess+0x50 to equal 2. The ordinary app-data construction branch writes 1
at 0x23b23, while only app ID 310 selects the adjacent value-2 branch at
0x23b17/0x24000.

The ordinary AppNavi ID-30 path therefore constructs the /dev/null literal at
0x46fab and calls QProcess::setStandardOutputFile at 0x16fbd and
QProcess::setStandardErrorFile at 0x17007. Client-side WAYLAND_DEBUG output is
thus predicted to be discarded rather than inherited by the launcher's own log.
This is static control-flow and object-construction evidence, not proof that the
runtime object was unmodified or that either redirection call succeeded.

or doneCurrent execution. No replacement runner or observation interposer was
created or executed for this record.
