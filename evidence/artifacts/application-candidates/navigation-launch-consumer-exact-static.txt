Status semantics in the concrete callbacks
------------------------------------------
Both concrete callbacks have the same decisive branch shape:

- if internal byte object+0x60+0x92 is already nonzero, log that current was
  play-enable true and return;
- otherwise, status other than 5 stores zero to that byte and returns;
- status 5 stores one to that byte and enters controller-mediated navigation
  handoff logic involving application ID 35.

The NaviMap callback's positive branch uses event constants 0x12e and 0x135.
The NaviMenu callback's corresponding branch uses 0x12e and 0x13f. Both retain
additional virtual predicates and controller dispatch; static reachability of
these blocks does not prove a runtime transition.

Conclusions and limits
----------------------
For these exact ApplicationManager consumers, integer 5 is the sole accepted
positive launch value. The sender-side signal member name containing "Fail" does
not determine the receiver's enum semantics. The observed pair status 5/window 0
therefore contains an accepted status blocked by an unset window latch; it is not
a two-field failure report.

The inspected routines contain no direct transition to Home application ID 11.
In the retained Home-to-Navigation-to-Home harness, the later return was
explicitly requested with event 302 and reason 322; it is not evidence of an
autonomous Navigation loading/fallback timeout. The positive callback path is
controller-mediated; static control flow does not prove the final current/drawing
application, callback delivery, surface composition, or successful
Home-to-Navigation transition.

The saved VM evidence still lacks the authentic AppNavi BG event that would call
